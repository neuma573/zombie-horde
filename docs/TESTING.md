# 테스트 원칙

이 문서는 Zombie Horde의 테스트를 일관되게 작성하고 배치하기 위한 기준을 정의한다.
테스트는 구현 세부사항이 아니라 게임의 판정, 상태 전이, 설정 계약을 검증해야 한다.

## 목표

- Phaser와 분리된 게임 판정을 빠르고 결정적으로 검증한다.
- 시간, 입력, 공간, 난수에 의한 비결정성을 통제한다.
- 실패한 테스트만으로 어떤 게임 규칙이 깨졌는지 알 수 있게 한다.
- 리팩터링 시 동작이 유지되는 한 테스트가 불필요하게 실패하지 않게 한다.
- 게임 판정과 시각 효과의 테스트 경계를 분리한다.

## 테스트 계층

모든 테스트 파일은 다음 계층 중 하나에 속해야 한다. 한 파일에서 여러 계층을
혼합하지 않는다.

### Unit

Phaser에 의존하지 않는 순수 함수와 값 객체를 검증한다.

- 대상: 이동, 조준, 충돌, hitscan, 피해, 웨이브, spawn, 시간 계산
- 실제 시간, 브라우저, Scene, 전역 상태를 사용하지 않는다.
- 입력과 반환값 또는 명시적으로 반환된 다음 상태를 검증한다.

### System

상태를 소유하고 여러 순수 로직을 조정하는 시스템의 공개 행위를 검증한다.

- 대상: `WeaponSystem`, `DamageSystem`과 같은 상태 보유 객체
- private 필드나 내부 호출 순서가 아닌 공개 메서드와 공개 상태를 검증한다.
- 각 테스트는 새로운 시스템 인스턴스를 사용한다.

### Scenario

여러 시스템을 연결한 핵심 플레이 흐름을 검증한다.

- 대상: 사격부터 좀비 사망까지, 웨이브 종료, 게임 오버와 재시작
- 개별 수학 공식과 경계값은 Unit 테스트에 맡긴다.
- 핵심 사용자 흐름만 소수로 유지한다.
- 테스트용 시뮬레이터는 프로덕션 규칙을 다시 구현하지 않고 기존 로직을 조정해야 한다.

### Contract

게임 디자인과 실행 환경에서 반드시 유지되어야 하는 설정 계약을 검증한다.

- 대상: 밸런스 의도, Phaser 설정, HTML 진입점, 배포 설정
- 정확한 숫자보다 플레이 의도를 우선해 표현한다.
- 정확한 수치 자체가 계약일 때만 숫자를 직접 고정한다.
- 소스 문자열 검사는 구조화된 값을 import하거나 실행해 검증할 수 없을 때만 사용한다.

### Browser

실제 브라우저와 Phaser의 연결을 검증한다.

- 대상: 게임 부팅, Scene 전환, 입력 연결, 반응형 화면, 치명적 콘솔 오류
- 세부 게임 규칙을 중복 검증하지 않는다.
- 브라우저 테스트는 느리고 실패 원인이 넓으므로 최소한의 smoke test로 유지한다.

## 디렉터리 구조

테스트는 `src/tests` 아래에서 계층과 도메인이 드러나도록 배치한다.

```text
src/tests/
  unit/
    combat/
    player/
    weapon/
    zombie/
    wave/
    world/
    ui/
  system/
  scenario/
  contract/
  fixtures/
```

- 디렉터리 이름은 테스트 계층을, 하위 디렉터리는 게임 도메인을 나타낸다.
- 공용 fixture는 `fixtures`에 두되, 하나의 파일에서만 사용하는 fixture는 해당 테스트
  파일 안에 둔다.
- 프로덕션 책임이 다르면 테스트 파일도 분리한다.
- `utils`, `misc`, `common`처럼 책임을 알 수 없는 이름은 사용하지 않는다.

## 파일과 테스트 이름

- 파일 이름은 검증 대상 또는 행위를 나타내고 `.test.ts`로 끝낸다.
- 테스트 본문은 `it`으로 통일한다.
- `describe`는 프로덕션 책임 또는 공개 API의 이름을 사용한다.
- `it` 이름은 영어 현재형 동사로 시작하고 관찰 가능한 행위를 설명한다.
- `works`, `handles correctly`, `test weapon`과 같은 모호한 이름은 사용하지 않는다.
- 구현 방법보다 게임 규칙을 표현한다.

```ts
describe('weapon reload', () => {
  it('loads only the available reserve ammo', () => {
    // ...
  });
});
```

## 테스트 구성

테스트는 Arrange, Act, Assert 순서로 읽혀야 한다. 구분이 명확하다면 주석을 반복해
작성할 필요는 없다.

```ts
it('loads only the available reserve ammo', () => {
  const state = createWeaponFixture({
    magazineAmmo: 0,
    reserveAmmo: 2,
  });

  const result = completeReload(state);

  expect(result.magazineAmmo).toBe(2);
  expect(result.reserveAmmo).toBe(0);
  expect(result.reloadRemainingMs).toBeNull();
});
```

- 하나의 테스트는 하나의 행위를 검증한다.
- 같은 행위의 결과를 설명한다면 여러 assertion을 사용할 수 있다.
- 서로 다른 이유로 실패할 수 있는 행위는 별도 테스트로 나눈다.
- 테스트 본문에 긴 반복문이나 조건문이 필요하면 시나리오 helper 추출을 검토한다.
- 정상 경로뿐 아니라 의미 있는 경계와 실패 경로를 검증한다.

## 공개 행위 검증

테스트는 공개 입력과 관찰 가능한 결과를 기준으로 작성한다.

다음 검증은 피한다.

- private 필드 접근
- Scene 자식 배열의 인덱스나 내부 생성 순서
- 결과와 관계없는 내부 메서드 호출 횟수
- 코드 정렬이나 함수 추출에 영향받는 소스 문자열
- 테스트만 통과시키기 위해 노출한 프로덕션 내부 상태

구현을 바꾸어도 같은 게임 행위를 제공한다면 기존 테스트는 그대로 통과해야 한다.

## Fixture

Fixture factory는 완전하고 유효한 기본 객체를 반환해야 한다.

```ts
function createZombieFixture(
  overrides: Partial<ZombieState> = {},
): ZombieState {
  return {
    id: 'zombie-1',
    health: 100,
    position: { x: 200, y: 100 },
    active: true,
    ...overrides,
  };
}
```

- 테스트는 관심 있는 값만 override한다.
- fixture 내부에서 현재 시간이나 난수를 사용하지 않는다.
- mutable fixture를 테스트 간 공유하지 않는다.
- 동일한 fixture가 3개 이상의 파일에서 반복될 때 공용 fixture로 승격한다.
- 공용 fixture에 도메인 행위나 assertion을 숨기지 않는다.

## 시간과 프레임 속도

게임 시간은 실제 timer나 대기 함수가 아니라 명시적인 `deltaMs`로 진행한다.

시간 기반 로직은 필요한 범위에서 다음 경계를 검증한다.

- 경계 직전
- 정확한 경계
- 경계 이후 또는 큰 delta
- 0, 음수, `NaN`과 같은 잘못된 delta

프레임 분할에 따라 결과가 달라질 수 있는 로직은 같은 총 시간을 서로 다른 delta로
나누어도 결과가 같음을 검증해야 한다.

```ts
const singleStep = simulate([1_000]);
const splitSteps = simulate(Array.from({ length: 60 }, () => 1_000 / 60));

expect(splitSteps).toEqual(singleStep);
```

부동소수점 누적값은 의도한 정밀도로 `toBeCloseTo`를 사용한다.

## 공간과 충돌

공간 판정에는 일반적인 정상 사례 외에 다음 경계를 고려한다.

- 두 객체가 정확히 닿는 경우
- 경계보다 아주 조금 안쪽과 바깥쪽인 경우
- 두 객체의 중심 좌표가 같은 경우
- 사거리와 viewport의 끝에 있는 경우
- 장애물 또는 화면 모서리를 스치는 경우
- 여러 대상이 같은 조준선에 겹치는 경우
- 폭이나 높이가 매우 작은 화면인 경우

위치, 거리, 각도, 정규화 벡터는 `toBeCloseTo`를 사용하고, 탄약, 체력, ID,
phase와 같은 이산 값은 정확히 비교한다.

## 난수와 결정성

- 난수 기반 로직은 seed 또는 주입 가능한 random source를 사용한다.
- 같은 seed와 입력은 같은 결과를 만들어야 한다.
- 테스트 기대값을 계산할 때 `Math.random()`을 직접 사용하지 않는다.
- 여러 번 실행한 통계 결과로 확률 로직을 판정하지 않는다.
- 시간, 실행 순서, 다른 테스트의 상태가 결과에 영향을 주어서는 안 된다.

## 불변 조건

개별 사례와 함께 도메인의 불변 조건을 검증한다.

- 체력과 탄약은 0 미만으로 내려가지 않는다.
- 진행률은 정의된 범위를 벗어나지 않는다.
- 위치와 방향에 `NaN` 또는 무한대가 생기지 않는다.
- 유효한 게임 객체는 허용된 월드 영역을 벗어나지 않는다.
- 한 simulation step에서 같은 판정이 중복 적용되지 않는다.

## 밸런스 테스트

밸런스 테스트는 순수 로직 테스트와 분리한다.

```ts
it('requires four pistol body shots to kill a base zombie', () => {
  const shots = Math.ceil(
    ZOMBIE_CONFIG.health / PISTOL_WEAPON.config.damage,
  );

  expect(shots).toBe(4);
});
```

- 가능한 경우 개별 설정값보다 플레이 결과를 계약으로 표현한다.
- 개별 값 자체가 디자인 계약이면 정확한 값을 검증한다.
- 테스트에서 프로덕션 계산 공식을 그대로 복제하지 않는다.
- 밸런스 변경은 관련 Contract 테스트를 의도적으로 갱신한다.

## 판정과 시각 효과

게임 판정과 시각 효과는 별도로 검증한다.

- 명중, 피해, 사망은 시각 효과 없이 검증할 수 있어야 한다.
- tracer, muzzle flash, hit effect는 판정 결과를 입력받아 표시되는지만 검증한다.
- 효과 테스트에서 hitscan이나 피해 공식을 다시 계산하지 않는다.
- 시각 효과의 구체적인 Phaser 내부 구조보다 계산 가능한 pose와 표시 상태를 우선
  검증한다.

## Mock과 테스트 격리

- Phaser 전체를 정교하게 mock하지 않는다.
- Phaser 경계가 필요한 행위는 작은 adapter로 분리하거나 Browser 테스트로 검증한다.
- 테스트마다 새로운 mutable state와 시스템 인스턴스를 생성한다.
- fake timer, spy, 전역 mock을 사용했다면 테스트 종료 전에 복원한다.
- 테스트 실행 순서에 의존하지 않는다.
- `.only`, `.skip`, 조건부 무시는 커밋하지 않는다.
- flaky test를 재시도 횟수 증가로 숨기지 않는다.

## Snapshot

Snapshot은 큰 객체를 간편하게 고정하기 위한 기본 수단으로 사용하지 않는다.

- 핵심 게임 규칙은 명시적인 assertion으로 표현한다.
- snapshot은 안정적인 직렬화 결과 전체가 실제 계약일 때만 사용한다.
- snapshot 갱신 전에는 변경된 모든 값을 검토한다.
- 의도를 설명할 수 없는 대형 snapshot을 추가하지 않는다.

## 커버리지

커버리지는 누락 가능성을 찾는 보조 지표이며 테스트 품질의 목표가 아니다.

- 커버리지 수치를 높이기 위한 의미 없는 테스트를 작성하지 않는다.
- 신규 분기에는 정상, 경계, 실패 경로 중 도메인에 필요한 사례를 추가한다.
- 커버리지 기준을 도입하거나 변경하는 작업은 현재 기준선과 제외 이유를 함께
  기록한다.

## 테스트 변경 규칙

- 기존 테스트를 삭제하거나 assertion을 완화하지 않는다.
- 기존 테스트가 잘못된 계약을 표현한다면 구현 전에 충돌 지점을 보고한다.
- 테스트 리팩터링에서는 행위와 assertion을 유지한다.
- 테스트와 프로덕션 코드를 함께 변경할 때는 변경된 요구사항을 테스트 이름과
  assertion에 드러낸다.
- 프로덕션 버그를 수정할 때는 가능하면 수정 전에 재현 테스트를 추가한다.

## 완료 조건

테스트와 관련된 변경은 다음 조건을 모두 만족해야 한다.

- 테스트가 올바른 계층과 도메인에 배치되어 있다.
- 시간 기반 로직은 필요한 경우 프레임 분할 독립성을 검증한다.
- 난수 기반 로직은 결정적으로 검증한다.
- 게임 판정과 시각 효과가 분리되어 있다.
- 기존 테스트가 삭제되거나 완화되지 않았다.
- `.only`, `.skip`, 임의의 snapshot 갱신이 없다.
- `npm test`가 통과한다.
- `npm run build`가 통과한다.
- 변경 파일, 설계 이유, 알려진 문제를 기록한다.
